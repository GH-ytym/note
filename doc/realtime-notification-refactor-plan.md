## 1. 先看这一页：我们到底要做什么

例如用户 A 申请加入 B 的群：

1. A 提交申请，数据库保存申请。
2. B 在线时，很快收到申请通知。
3. B 不在线时，下次打开也能看到申请。
4. B 同意后，数据库保存成员关系和审核结果。
5. A 收到结果，B 的其他窗口也显示“已同意”。
6. 网络断开再恢复，补上遗漏的变化。
7. 重复投递或重复点击，不会重复加群、重复计算未读数。

同时，日常读取和断线补收尽量使用 Redis，减少每个窗口反复查询 SQLite。

**固定技术路线：SQLite + Outbox + RabbitMQ + Redis + SSE。**

不在本轮引入 Kafka，不改成 WebSocket，不拆成多个微服务。先在一个 Go 应用中组织好模块；Redis、RabbitMQ 作为独立服务运行。

这里有一个必须记住的区别：

- **写业务：先提交 SQLite。**审核是否成功、用户是否已入群，都以数据库为准。
- **读通知：优先 Redis。**缓存缺失、不能信任或故障时，才使用数据库恢复。

RabbitMQ 是结合学习消息队列的目标加入的。它负责后台任务的缓冲、确认和重新投递；减少 SQL 读取主要靠 Redis 缓存与增量同步。加入 MQ 不代表所有操作都会更快。

## 2. 本计划采用的产品行为

以下是本计划的默认选择。后续若用户明确要求改变，应先更新本文，再修改代码。

| 问题 | 本计划的选择 |
| --- | --- |
| 通知里的昵称、头像、群名 | 保持当前行为，显示最新资料，允许正常同步延迟 |
| 审核状态从哪里判断 | SQLite；不能根据 Redis 卡片决定是否允许审核 |
| 操作成功是什么意思 | SQLite 事务提交成功；不等于所有窗口已经同步 |
| Redis 暂时落后怎么办 | 允许短暂延迟，随后补齐；操作窗口先展示“操作成功，正在同步” |
| 一次展示多少条 | 最近 50 条，按通知 ID 倒序，与当前代码一致 |
| 未读数量 | 全部通知的未读数，不只是最近 50 条 |
| 通知已读与申请已处理 | 两件事，分别保存，不能互相代替 |
| 多窗口 | 继续支持；共享服务端数据，每个窗口记录自己的同步进度 |
| 历史很久以前已过期 | 重新加载当前通知面板；不承诺无限补播所有中间过程 |

为控制教学难度，第一版**不做“先修改卡片、以后再撤销或确认”的复杂乐观更新**。点击审核成功后，显示成功反馈并暂时禁用该操作，主动启动同步；卡片的正式状态由完整快照或连续事件更新。

操作接口可以返回当前用户的目标版本。前端等待同步至少达到这个版本，不能仅因为接口成功就跳过中间事件。

“最新资料”有成本：用户改名、换头像或群改名，也要通知受影响的通知面板更新。只更新资料表而不处理缓存，不算完成该功能。

## 3. 先认识几个词

| 名称 | 可以这样理解 |
| --- | --- |
| Notification | 数据库里的一条通知，如“有人申请加群” |
| Card | 前端展示这一条通知需要的数据 |
| Inbox | 当前通知面板：最近 50 张卡片、未读总数、版本 |
| Outbox | 与业务一起保存的“待发送任务清单” |
| RabbitMQ | 接收任务，交给后台消费者处理；处理失败可以重投 |
| Redis 面板缓存 | 用户现在打开通知面板应该看到什么 |
| Redis 变化历史 | 最近发生过哪些变化，用于断线补收 |
| Pub/Sub | 提醒在线后端“刚刚有新变化”；它不负责保存历史 |
| Hub | Go 内存中，某个用户的所有 SSE 连接集合 |
| SSE | Go 向浏览器持续发送事件的 HTTP 连接 |
| revision（版本） | 某个用户的通知面板发生了第几次变化 |
| epoch（缓存代次） | 这一套 Redis 面板和历史属于哪一次有效构建 |
| ACK | 消费者告诉 RabbitMQ：“这个任务处理完了” |
| reset | 原来的断点不能继续使用，请重新装入完整面板 |

版本属于用户，不属于窗口。用户 8 开三个窗口，服务端仍只有一套用户 8 的版本；三个窗口可能分别收到第 20、21、22 版。

## 4. 固定的整体链路

```text
申请 / 邀请 / 审核 / 已读等业务接口
    ↓
SQLite 同一个事务
    ├─ 修改业务数据和通知
    ├─ 更新受影响用户的版本、未读数
    └─ 保存 Outbox
    ↓
Outbox 发布器
    ↓ 发布，并等待 RabbitMQ 确认接收
RabbitMQ
    ↓
通知消费者
    ├─ 更新 Redis 当前面板
    ├─ 追加 Redis 近期变化历史
    └─ 通过 Redis Pub/Sub 广播
    ↓ 更新成功后，向 RabbitMQ ACK
后端订阅器 → Hub → 各窗口 SSE
    ↓
前端按版本更新通知面板
```

读取与恢复走另一条路径：

```text
第一次打开：Redis 当前面板 → 没有有效缓存才查 SQLite
短暂断线：Redis 近期历史 → 补上缺少的变化
历史过期：Redis 当前面板 → 替换旧面板
Redis 缓存失效：SQLite → 重建 Redis → 返回完整面板
```

## 5. 现有代码哪些复用，哪些替换

| 现有内容 | 处理方式 | 原因 |
| --- | --- | --- |
| 申请、通知、Outbox 同事务保存 | 保留 | 防止业务成功但任务没有保存 |
| `internal/model/join.go` | 保留并补齐业务规则 | 已经表达申请、邀请与审核状态 |
| `internal/model/notification.go` | 保留并扩展类型、迁移 | 仍是持久化通知记录 |
| `internal/notification/dto.go` 的 Card | 保留主要字段 | 前端仍需要这些展示数据 |
| `NotificationState` | 保留方向，补版本与未读数的完整维护 | 当前字段本身还不构成同步机制 |
| `internal/model/outbox.go` | 保留用途，调整任务内容和字段含义 | 改为交给 MQ 的变化任务 |
| `internal/notification/outbox_worker.go` | 拆为发布器与消费者 | 发送到 MQ 和更新 Redis 是两步 |
| `internal/notification/snapshot.go` | 替换职责 | 不再每次业务变化都查询并入队完整面板 |
| `internal/notification/redis_publisher.go` | 重写核心逻辑 | 需要同时维护当前面板、历史和版本 |
| `internal/notification/redis_history.go` | 保留 Stream 查询经验，重写返回协议 | 要说明历史完整、需继续分页或必须 reset |
| `internal/notification/redis_subscriber.go` | 复用分发结构，增加恢复校正 | 自动重订阅不等于没有漏事件 |
| `internal/notification/hub.go` | 基本复用 | 多窗口分发、慢连接隔离仍然有用 |
| `internal/handler/notification_handler.go` | 复用鉴权、心跳、超时，重写同步部分 | SSE 传输没有必要推倒 |
| `web/src/hooks/useNotifications.ts` | 保留认证、取消、重连思路，重写状态更新 | 收到事件后不再默认查询 SQL |
| `web/src/lib/notification-stream.ts` | 扩展为解析完整事件 | 不能只识别事件名字而忽略数据与版本 |

取消的做法：每次推送后查完整 SQL 列表、每个窗口定期查完整 SQL 列表、每次变化构造完整 Inbox 放进 Outbox、无限增长的 Redis sent 去重表。

“取消完整快照入队”不等于取消快照。快照仍用于初始加载和 reset。

## 6. 数据库应该保存什么

### 6.1 业务表保持原来的职责

- `group_join_requests`：申请、邀请、待审核或已处理状态。
- `group_members`：最终成员关系，群与用户组合唯一。
- `notifications`：通知接收者、关联业务、通知类型、已读时间。

审核必须在事务内检查权限、有效期和当前状态，使用带 `pending` 条件的更新，并检查实际修改行数。重复请求不能重复加群或重复发结果通知。

### 6.2 用户通知状态

`notification_states` 每用户一行：

| 字段 | 含义 |
| --- | --- |
| `user_id` | 用户 ID，主键 |
| `revision` | 当前数据库通知版本 |
| `unread_count` | 当前全部未读数 |

同一次业务事务对同一用户造成多张通知变化，只增加一次版本、生成一条任务。不同接收者各有自己的版本。

第一版在实际业务变化后，使用现有接收者/已读索引统计一次该用户未读数，再写入状态表。这样比手工维护许多加减分支更容易验证。该查询按业务变化发生，不按窗口数发生；缓存读取不再 COUNT。

如以后实测统计成为瓶颈，再在保持协议不变的前提下，优化为按实际修改行数维护计数。

### 6.3 Outbox

新任务至少表达：任务 ID、接收者、用户版本、协议版本、变化类型、JSON 内容、创建时间、MQ 确认时间。

旧 `PublishedAt` 的含义必须调整，建议改名 `BrokerConfirmedAt`：只表示 RabbitMQ 已接管任务，不表示 Redis 已更新，更不表示用户已读。

发布失败还需要记录重试时间、次数、最近错误。已完成任务按保留策略清理，不无限增长。

### 6.4 现有数据库怎么升级

教学先使用独立测试数据库；不能通过删除用户现有数据库来让测试通过。

旧 Outbox 没有有效版本，不能给同一用户的所有旧任务统一填 `0` 后建立唯一索引。

迁移要单独设计并测试：保留原业务与通知数据，初始化每个用户的版本和正确未读数，把旧格式待投递任务转换为明确的重建任务或归档后生成替代任务。只有替代任务保存成功，旧任务才可以停止消费。

迁移必须可重复执行；旧通知的主键、已读时间和申请关联不能被改变。

## 7. 后台任务与前端事件的约定

### 7.1 两种后台任务就够了

1. `change`：普通新增、审核、已读，包含本次变动的完整 Card 和变化后的未读总数。
2. `rebuild`：删除补位、群解散、关联资料变化等情况，要求重新构建该用户的当前面板。

普通任务示意，Card 字段有省略：

```json
{
  "schema_version": 1,
  "user_id": 8,
  "revision": "21",
  "kind": "change",
  "upserts": [{"id": 103, "request_status": "accepted"}],
  "unread_count": 4
}
```

这是协议示例，不是可以直接粘贴的 Go 结构体。

`upserts` 的意思：存在就替换，不存在则按列表规则考虑加入。普通任务携带足够数据，消费者不应为了处理每条任务重新查 SQL 关联资料。

### 7.2 SSE 只定义清楚三类消息

| 消息 | 用途 |
| --- | --- |
| `snapshot` | 完整面板，包含 epoch、revision、items、unread_count |
| `change` | 同一 epoch 下的一次连续变化 |
| `reset` | 当前游标不能继续使用，启动完整同步 |

心跳仍保留；心跳表示连接活着，不表示业务状态完整。

版本在 JSON 中使用字符串，前端不要转成普通 Number 后比较；可以使用 BigInt。Redis 脚本也不能随意把大版本号转成 Lua 浮点数，可使用字符串比较与预期版本校验。

### 7.3 最近 50 条规则

- 固定按通知 ID 倒序排列，最多 50 条。
- 更新不改变通知 ID，不因为“刚审核”就置顶。
- 面板外的旧通知更新后仍按 ID 排序、截断；不能直接塞到最前面。
- 未读数直接使用事件里的绝对值，不能由当前 50 张卡片推算。
- 删除、解散导致列表需要补位时，第一版走 rebuild 和完整同步。

Redis 和前端必须使用同一套含义的列表规则，分别有测试。

## 8. RabbitMQ 第一版怎么使用

开始只建一条通知任务队列，使用一个活跃消费者，串行处理。先把正确性学会，再根据测试结果调整吞吐量。

### 发布器

1. 按顺序读取未完成 Outbox，支持批量查询。
2. 发布持久消息到持久队列。
3. 等待发布确认，并处理无法路由的消息返回。
4. 确认成功后才记录 `BrokerConfirmedAt`。
5. 确认丢失或记录失败时，允许再次发布同一任务。

### 消费者

1. 验证消息格式。
2. 检查 Redis 缓存和版本。
3. 应用变化，或重建当前面板。
4. Redis 操作成功后手动 ACK。

必须接受这样的情况：Redis 已更新，进程在 ACK 前退出，RabbitMQ 又发来同一任务。版本判断保证它不会再次修改状态或重复计数。

Redis 暂时不可用时退避等待，不立即无限 nack/requeue 制造空转。持续失败、无法处理的消息进入可检查的失败流程；死信是保存失败任务的地方，不是让问题自动消失。

对于有合法接收者的坏任务，要记录失败并触发该用户的缓存修复。用户无法识别的坏消息需记录任务 ID，由故障处理流程定位。不能跳过消息后直接应用不连续版本。

后续若需要并行：按用户 ID 分到固定数量的队列，同一用户进入同一条队列。不能简单开启许多消费者后假设处理顺序不变。

单台机器上的单节点 RabbitMQ 可以学习、运行，但不提供多节点容灾。部署前要明确队列类型、持久卷和备份，不把“持久化”说成“绝不丢失”。

## 9. Redis 第一版怎么组织

保留“每用户一份面板、一份近期历史”，不为每个窗口复制。

建议第一版的面板缓存使用一个完整 JSON 值，最多 50 张卡片，包含 epoch、revision、items 和 unread_count；另用 Stream 保存近期变化。这样初始读取不会拿到来自不同版本的卡片与计数，代码也比较容易理解。

普通变化可在 Go 中读取并修改这份小面板，再用 Redis 脚本按预期 epoch 和 revision 条件写回，同时追加历史并广播。竞争导致条件不满足时，重新读取并判断。

**这里可能重新编码最多 50 张卡片，但不会每次查 SQL，也不会每次把 50 张卡片都推给客户端。**这是第一版为实现简单而接受的有限 Redis 读写开销；后续只有测量证明有问题才更换内部存储形式，外部协议不变。

### 应用版本规则

假设 Redis 当前版本是 20：

- 收到 21：正常应用。
- 收到 20 或更小：不重复修改。
- 收到 22 或更大：不能直接跳过去。本计划第一版从 SQLite 重建当前面板，建立新恢复基线。
- 缓存不存在：同样先重建，不假装从空面板开始补一个任意版本。

重建可以读到数据库版本 25。这时缓存直接建立完整的版本 25，并通知客户端 reset；以后迟到的 21～25 不再重复应用。允许跳过的前提是**已经装入完整状态**，不能把这个规则用于不完整的增量事件。

### 历史保存规则

- 配置最大条数与保留时间，两者都有上限。
- 保存明确的缓存代次与恢复起点；不能把空历史当作“用户没有漏消息”。
- 历史分页必须覆盖到本次恢复选定的目标版本，不能查到 100 条就认为结束。
- 只要无法证明版本连续，就 reset。
- 面板、历史、恢复元数据的生命周期要一起设计；某个 key 还在不代表整套缓存有效。
- 不保存无限增长的 sent Hash；同一代次内以已应用版本防重复，重建后用完整快照版本判断旧任务。

## 10. 四条上线与恢复路径

### A. 第一次上线，没有本地通知状态

1. 校验登录，只能订阅当前用户。
2. 后端先登记实时订阅，暂存期间到来的事件。
3. 从 Redis 读取完整面板；没有有效缓存才重建。
4. 向前端发送 `snapshot`，例如版本 20。
5. 丢掉暂存的 20 及以前事件，连续发送 21、22……

缓冲队列满、代次改变或版本出现缺口时，重新同步，不能悄悄漏掉。

### B. 短暂断线，页面还保留版本 20 的完整面板

1. 重连时携带 epoch 和 revision=20。
2. 后端先接住实时事件，再确定恢复目标版本。
3. Redis 历史完整时，分批补齐 21 到目标版本。
4. 然后衔接实时事件，过滤重复。

游标代表“已成功应用”，不是“网络收到过”。前端更新状态成功后才推进游标。

### C. 断线太久，历史已经过期

不需要先查询 SQLite。先读取仍有效的 Redis 面板，发完整 snapshot，继续实时同步。

### D. Redis 面板也丢失或无效

同一用户的并发恢复请求合并，减少重复查库。在数据库同一读取快照中读取列表、未读数和版本，再安全安装到 Redis。

安装必须同时检查重建令牌与缓存条件。例如重建读到 20，但另一路已经写入 21，不能把 20 覆盖上去。重建锁到期后，旧任务也不能继续写入。

锁用于合并工作，不代替条件写入。安装条件需要 Redis 原子检查；安装失败就重新判断，不盲目覆盖。

重建成功建立新的 epoch 和历史基线。Redis 恢复成旧数据、前端版本比缓存更高时，也不能让客户端直接倒退，应验证 SQLite 并修复。

### 注意：刷新页面不一定属于短暂断线

如果卡片状态丢了，只剩 localStorage 里的版本号，不能只补增量。第一版不持久化浏览器面板，刷新页面按首次上线处理；同一页面 SSE 重连才复用内存状态与游标。

## 11. 操作成功后为什么不能直接跳版本

```text
窗口当前是 20
21：新增通知 A，窗口还没收到
22：当前窗口审核通知 B，HTTP 请求成功
```

如果因为审核成功就把同步游标改成 22，之后的 21 会被丢掉，通知 A 就漏了。

本计划处理方式：显示成功反馈，保持游标 20，禁用已提交操作，主动补齐 21、22；追上后清除“正在同步”。如果短时间追不上，显示同步状态并允许重试，不能把已成功的审核说成失败。

群组列表、成员列表也会受到入群结果影响。第一版允许在相关事件到达时刷新这些业务列表；本计划优化的核心是通知面板，不承诺把全项目所有 SQL 查询一起消除。

## 12. 保留哪些轮询，取消哪些轮询

| 检查 | 做法 |
| --- | --- |
| 浏览器每分钟查完整通知 SQL | 正常模式取消 |
| 是否静默漏了最后一条事件 | 后端按在线用户合并检查 Redis 当前版本，促使落后窗口恢复 |
| Outbox 有没有新任务 | 提交后唤醒 + 定期扫描兜底，不依赖一次内存通知 |
| Redis 是否落后数据库 | 后台对活跃用户低频、分批检查数据库状态版本，发现异常重建 |

周期应做成配置，加入适量抖动，避免所有连接同时检查。上线前通过测量确定具体数值，不在未测试时承诺秒级上限。

RabbitMQ ACK 后 Redis 仍可能丢失数据，因此 MQ 不能取代数据库校验和重建。

Redis 故障时，可以降级到有频率限制、同用户请求合并的 SQLite 面板查询。此时显示同步服务降级，暂停使用 Redis 游标；Redis 恢复后重新建立快照。不能让每条失败 SSE 连接无限快速回查数据库。

## 13. 资料变化、删除和未读数不能漏掉

所有会改变通知面板的路径都必须进入统一的变化生成入口，包括：

- 新申请、邀请、直接入群提醒。
- 接受、拒绝、取消，以及实际生效的过期处理。
- 已读操作。
- 删除通知、解散群组导致的通知删除。
- 通知中涉及的昵称、头像、群名变化。

资料变化时，先找出受影响的通知接收者，在对应资料更新事务内推进这些用户的通知版本、生成 rebuild 任务。第一版接受这类低频操作的集中开销。

群删除不能只依赖外键级联：还要在删除前确定受影响用户，在同一事务中正确维护状态和任务。已删除群组的旧通知事件不能重新把卡片放回来。

目前模型中的 `JoinReviewed` 常量与数据库通知类型 CHECK 约束不一致，补审核时必须一起修改迁移和测试。

## 14. 分阶段教学步骤

每次只完成一个阶段中的一个小步骤。没有完成当前验证，不直接堆下一层。

### 阶段 0：保存现场，恢复一个明确的工作起点

- [ ] 阅读本文与项目实际代码，记录差异。
- [ ] 保留当前未提交改动，不能直接 reset 或覆盖用户代码。
- [ ] 使用独立测试数据库，记录当前失败测试。
- [ ] 清理半接入快照方案造成的断点，先恢复现有“收到推送后重查”的可运行基线。

阶段 0 的重查只是临时基线，不是最终方案。恢复基线时可能暂时移除尚未接好的版本约束，后续在完整迁移中重新引入，不能让它们继续拦截正常业务。

2026-10-09 已发现的起点问题：`notification_states` 没有建表迁移；snapshot 查询使用了错误的 `receiver_id`；前端不识别 snapshot 事件；旧任务 revision=0 与新增唯一约束冲突。

**通过标准：**原有申请、通知、Outbox、实时刷新相关测试恢复通过，双窗口链路重新可验证。

### 阶段 1：学习 RabbitMQ 的最小例子

- [ ] 解释队列、生产者、消费者、发布确认、ACK。
- [ ] 启动本地 RabbitMQ，创建与业务隔离的练习队列。
- [ ] 用很短的 Go 示例发送、消费一条消息。
- [ ] 在 ACK 前结束消费者，观察重新投递。
- [ ] 解释重复投递为什么正常，记录本地运行方式。

**通过标准：**用户能说清“发布确认”和“消费确认”分别确认什么。此阶段不修改真实入群链路。

### 阶段 2：定义变化协议，完成数据库部分

- [ ] 定义 change、rebuild 任务和 snapshot、change、reset SSE 消息。
- [ ] 完成状态表、Outbox 迁移。
- [ ] 写统一的事务内通知变化生成函数。
- [ ] 先只接入现有申请入群路径，验证版本、未读数、Outbox。
- [ ] 测试业务回滚时状态和任务一起回滚。
- [ ] 测试重复申请不会增加版本或重复通知。

**通过标准：**数据库生成正确任务，不依赖 MQ、Redis 正常运行才能验证。

### 阶段 3：实现 Redis 面板与历史

- [ ] 从数据库一致快照构建面板。
- [ ] 实现带条件的缓存安装，防止旧重建覆盖新状态。
- [ ] 实现 ApplyChange：更新面板、历史、广播。
- [ ] 完成版本连续性、重复处理和 rebuild。
- [ ] 完成历史容量、时间限制和缺口判断。
- [ ] 验证前 50 条、旧卡片更新、全部未读数。

**通过标准：**使用测试直接调用缓存模块即可验证；还不靠浏览器或 MQ 掩盖错误。

### 阶段 4：把 RabbitMQ 接入真实链路

- [ ] Outbox 发布器等待 MQ 确认后标记成功。
- [ ] 消费者调用阶段 3 已验证的缓存模块。
- [ ] Redis 更新成功后 ACK。
- [ ] 增加退避、失败记录与死信修复路径。
- [ ] 测试 MQ 断开恢复、重复消息、消费者中途退出。

**通过标准：**从真实申请到 Redis 更新可以跑通；重投不会重复产生状态变化。

### 阶段 5：SSE 与前端真正消费变化

- [ ] 首次连接发送 snapshot，后续发送 change。
- [ ] 前端解析数据、维护面板状态与游标。
- [ ] 统一列表排序、截断和未读数处理。
- [ ] 普通事件不再调用完整通知 SQL 查询。
- [ ] 保留登录续期、退出取消、多窗口隔离。

**通过标准：**多个窗口在线时直接更新通知；通过日志确认没有每事件回查 SQL。

### 阶段 6：完成断线恢复和降级

- [ ] 同一页面重连携带游标。
- [ ] 历史补收与实时事件正确衔接。
- [ ] 历史过期、缓存代次改变触发完整同步。
- [ ] Redis 丢失后合并重建，Redis 故障时受控降级。
- [ ] 增加在线版本校正与后台数据库校验。

**通过标准：**断网期间发生变化，恢复后无需手动刷新即可正确显示；漏掉最后一条广播也能被发现。

### 阶段 7：补齐用户真正要用的业务

- [ ] 申请通过与拒绝。
- [ ] 指定用户邀请、接受与拒绝。
- [ ] 已读操作。
- [ ] 删除、解散、资料变更、申请失效等相关路径。
- [ ] 操作成功后的同步提示与目标版本等待。
- [ ] 刷新相关群组、成员列表。

**通过标准：**A 申请、B 审核、A 收到结果；邀请链路也能完成。重复操作、多窗口操作都不会改变已完成的业务事实。

### 阶段 8：云端部署与性能检查

- [ ] 一个共享的云端 API，所有客户端连接它；不能各自使用独立 SQLite 并期待自动同步。
- [ ] SQLite、RabbitMQ 配置持久卷，数据库和队列有备份方案。
- [ ] 配置认证、SSE 代理缓冲与连接超时。
- [ ] 根据现有认证模块实际依赖验证 Redis 故障行为，不把通知降级误当成整个应用都可无 Redis 运行。
- [ ] 添加积压、失败、恢复、缓存命中与 SQL 回源指标。
- [ ] 用实际数据测量，再调整检查周期、批量大小和消费者吞吐量。

第一版只有一个负责 SQLite 的 API 实例，不让多台云服务器直接共享同一个 SQLite 文件。需要多 API 实例同时写入时，另立数据库迁移计划。

## 15. 必须通过的故障验证

| 场景 | 正确结果 |
| --- | --- |
| 业务事务失败 | 申请、通知、状态、Outbox 一起回滚 |
| MQ 已接收，但发布器没记录成功 | 允许再次发布，最终状态不重复 |
| Redis 已更新，消费者 ACK 前退出 | 再次消费不会重复计数、追加同一变化 |
| Redis 是 20，任务直接来了 22 | 不直接应用；重建完整状态并 reset |
| 重建读到 20，缓存已变成 21 | 旧重建不能覆盖新缓存 |
| 缓存重建锁过期，旧任务才返回 | 旧任务没有资格安装结果 |
| 面板是 101～150，通知 30 被更新 | 不挤掉通知 101；未读总数仍正确 |
| 删除当前列表中的一条 | 最近 50 条得到正确补位或完整替换 |
| 初始读取期间发生审核 | 最终显示审核后的状态，没有遗漏或倒退 |
| 操作响应是 22，但窗口还停在 20 | 仍补齐 21，不直接推进游标 |
| SSE 没断，Redis 广播漏了最后一条 | 版本校正发现并补齐 |
| Redis 历史被裁剪或丢失 | 不假报恢复成功，使用 snapshot |
| Redis 面板丢失或恢复为旧数据 | SQLite 修复，旧事件不能复活已删除通知 |
| 用户改名、换头像、群改名 | 当前列表和重建后的列表最终一致 |

这些测试用于验证同步边界，不只是检查几个函数是否被调用。缓存和队列测试优先使用隔离环境，不连接真实用户的数据。

## 16. 性能目标与检查方式

本计划不预先宣称能支持多少并发。先验证以下可观察目标：

- 热缓存下首次打开面板不查询通知 SQL。
- 在线普通变化不触发每窗口 SQL 查询。
- Redis 历史完整时，断线补收不查询通知 SQL。
- 同一用户多个窗口同时遇到冷缓存，回源请求能被合并。
- 无变化时，日常校正主要读取 Redis；SQL 校验按用户合并、低频执行。
- 业务事务仍正常写 SQL，Outbox 仍有扫描和确认写入，不能宣称“零 SQL”。

至少记录：Outbox 最老未发布任务年龄、MQ 积压与失败数、Redis 缓存命中率、SQL 重建次数、增量恢复成功数、reset 次数、同步延迟。

## 17. 后续教学必须遵守的方式

2. 每次先用一句话说明本小步的目的，再解释不超过几个必要概念。

4. **默认由用户自己编辑。助手不直接修改业务代码，除非用户明确授权这一次直接修改。**
5. 每小步给出验证命令与预期结果；出现错误先定位，不顺手加入另一套架构。
6. 不一次铺开所有模块。前面阶段通过后，才进入下一阶段。
7. 只有代码实际完成并验证后，才更新检查框和进度；讨论不算实现。
8. 确实发现本文不可行时，说明具体反例、必要调整及影响范围，再更新计划。不能仅凭偏好改换技术路线。
