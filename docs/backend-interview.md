# 协作日历 Go 后端面试复习笔记

按当前工作区源码整理，包含正在修改的通知模块。面试前先把第 1、3、4 节合上笔记讲一遍，再用第 7 节做追问练习。

## 1. 开场怎么讲

> 我做的是一个支持群组协作的日历后端。用户可以在群里建周期待办和有起止时间的日程，每个成员可以独立打卡，也可以给指定成员授予编辑权。后端用 Go、Gin 和 GORM，SQLite 保存业务数据，Redis 管刷新会话、通知列表和实时广播。我做这套设计时主要解决三个问题：退群后怎样立即收回权限，两个人基于同一份旧数据编辑时怎样避免覆盖，以及入群已经成功、通知还没发出去时怎样恢复。第三个问题我用同一个 SQLite 事务记录业务结果和 Outbox，再由后台任务更新 Redis，通过 SSE 通知在线用户。

如果面试官问“挑一个深入讲”，从**用户 B 加入 A 的公开群**讲起。先说 A 最终应该看到什么，再说后端在哪一步能向 B 返回成功。这个例子能自然带出权限、事务、重试和推送。

## 2. 在脑中重建这套服务

| 从哪里看 | 它回答什么问题 |
| --- | --- |
| `cmd/api/main.go` → `internal/app.go` | 一个 Go 进程如何组装 SQLite、Redis、各模块、HTTP Server、Outbox worker 和订阅协程 |
| `internal/router/router.go` → `middleware` → `handler` | 哪些 API 已经挂出来，身份来自哪里，HTTP 状态码如何产生 |
| `internal/{auth,group,todo,event,calendar,search,profile}` | Service 负责规则与编排，Repository 负责 SQL、授权查询和事务，Calendar 只依赖两个小接口 |
| `internal/model`、`internal/migration.go` | 哪些关系由唯一索引、外键、CHECK 兜底，旧数据库怎样升级 |
| `internal/notification` | 哪些数据持久化，何时重建缓存，在线连接怎样获得变化 |

**数据模型串起来记。** 用户和群通过 `group_members` 形成多对多。每条 Todo 或 Event 属于一个群、一个创建者，各自另有成员角色表和自定义日期表。Todo 的完成记录按“任务＋发生日”唯一。入群申请有申请人、接收人和处理状态。通知有接收者和已读时间，审批进度与是否已读可以独立变化。每个接收者有一行通知状态保存业务版本与未读总数。Outbox 保存一批变化的载荷和投递进度。

**启动和停机。** 默认打开 `data/note.db`、执行迁移、验证 JWT 配置、Ping Redis。Redis 是当前启动依赖。程序先等 Redis 确认模式订阅，再启动投递循环和 HTTP 服务，避免本进程刚开始投递时订阅尚未就绪。关闭时取消后台 context、关闭 Hub 让 SSE 退出，用新的 10 秒 context 等 HTTP 请求收尾，超时强制关闭，等待后台循环退出后再释放底层连接。

**迁移举例。** 为旧日程增加群组归属时，已有数据且无法确定创建者或群组，迁移会报错要求回填。补 Event 成员角色用 `WHERE NOT EXISTS`，重复启动不会把已经提升为 editor 的成员刷回 viewer。注册新用户时，用户与零值通知状态在同一事务创建，后续增加未读数才能直接更新已有状态行。

## 3. 最值得练的项目深挖：一次入群，群主怎样收到通知

1. **请求。** B 请求 `POST /api/groups/join`。中间件校验 Bearer JWT，handler 从上下文取 B 的身份。Service 去除群号首尾空格、转大写、检查六位字母数字格式。群号公开，授权仍由数据库中的群策略和成员关系决定。
2. **事务内决定入群结果。** Repository 用当前群策略判断。已经是成员就直接返回。公开群为 B 写入成员关系，补现有 Todo/Event 的条目角色，同时为群主 A 创建 `joined` 通知。审核群写 `pending` 申请及 `join_requested` 通知，七天内已有有效待处理申请则复用。公开群成功返回 200，等待审核返回 202。受限群拒绝按号加入，个人群在群号查找时排除。当前创建群组的入口默认建公开群，路由能看到申请入口，未挂出同意、拒绝或邀请的完整 API。
3. **记录发送意图。** 写通知后，对同一事务调用 `EnqueueChange`。A 的 `revision` 加一，本例未读数加一。将卡片变化、版本和更新后的未读总数写入 Outbox。任何一步失败都返回错误，使成员、初始角色、通知、计数和任务一起回滚。事务提交后就能回复 B，A 可以稍后收到消息。
4. **后台投递。** Worker 启动立即跑一轮，随后按一秒节拍执行，每轮共用五秒超时，按 ID 升序取最多 100 条未标记的任务，逐条处理。投递确认缓存已覆盖目标版本后才写 `published_at`。某条失败或暂未完成会结束本轮，留给下一轮。
5. **更新通知列表。** 每个用户有一个 state Hash（版本、未读数等）、items Hash（ID 到卡片 JSON）、order ZSet（ID 倒序分页）、history Stream（近期事件）和 live Pub/Sub 频道。Lua 检查版本后更新卡片和顺序、追加 Stream、更新状态、广播。增量历史上限 1000 条。未读数使用业务事务给出的最终值，重放旧任务时不会累加第二次。
6. **到达连接。** 进程订阅 live 频道，按接收者 ID 调用 Hub。每条 SSE 连接有自己的缓冲 channel，同一用户打开两条连接，两边都能收到。Handler 写 SSE 事件并 Flush，空闲时每 15 秒发心跳。连接的截止时间受 access token 到期时间约束。

**把四个故障点讲熟。**

| 面试官给的故障 | 当下会发生什么 | 后续怎样收敛 |
| --- | --- | --- |
| SQL 提交前写 Outbox 失败 | 事务回滚，B 没有部分入群 | 调用方可以重新发起请求 |
| SQL 已提交，进程还没更新 Redis 就退出 | B 已入群，A 的缓存可能暂时落后 | 重启后 worker 还能查到未标记任务 |
| Redis 已更新，进程没来得及写 `published_at` | 同一任务会再次投递 | Lua 发现该版本已被覆盖，worker 可补标完成 |
| A 断网，或其连接队列已满 | 在线广播可能错过，数据库通知依然存在 | 重新查列表可恢复当前状态。v2 有历史读取脚本及测试，当前 SSE handler 尚未接入游标补发 |

**缓存断档怎么修？** 假设缓存是第 8 版。来第 8 版可以忽略，第 9 版正常应用，直接来第 10 版就需要重建，因为漏掉的第 9 版可能改了另一张卡片。重建者拿一个按用户划分的 5 秒租约，记住当时 Redis state，在 SQLite 的同一个只读事务中取完整卡片、版本和未读数。安装前再检查租约 token 与先前 state；期间有增量写入，旧快照就不能覆盖新状态。成功安装会换 epoch、重置历史并记录 reset。只有快照版本覆盖了目标任务，worker 才能标记它完成。

**四个容易混淆的量。** 卡片 ID 用于列表分页，`before` 取严格小于上一页最后一条 ID 的记录，额外多取一条判断是否还有下一页。`revision` 是每个用户的业务变化次序。`epoch` 区分缓存重建前后两代。`head_id` 是当前代最后一个 Stream 事件的位置。即使重建前后业务数据同为第 9 版，新历史的位置也可能完全不同。

**读取失败时怎样答？** 列表优先从 Redis 原子读取一页及同步位置。判断缓存需要恢复时，最多一次重建、再读一次，仍不可用返回对应的 503。Redis 命令执行错误会沿错误路径返回，handler 的通用错误为 500。数据库完整快照供重建使用。返回空列表会让用户误以为自己没有通知。

源码入口可按顺序搜索 `group.Join`（仓库方法 `Join`）、`EnqueueChange`、`PublishPending`、`Delivery.Deliver`、`apply_change.lua`、`RunRedisSubscriber`、`Hub.Send`、`NotificationHandler.Stream`。

## 4. 协作编辑和日历是怎么实现的

### 同一份日程，三层权限分别管什么？

| 身份 | 能做什么 |
| --- | --- |
| 当前群成员 | 查看群内日程、搜索，给自己的某次待办打卡 |
| 该条目的 editor | 在仍是群成员的前提下修改条目内容 |
| 该条目的创建者 | 在群内可以修改、删除、调整条目角色 |
| 群主 | 管群组，例如转让群主和解散。编辑他人条目仍走条目权限 |

新建条目时给现有群成员初始化角色，创建者为 editor，其余为 viewer。入群时反过来给新成员补现有条目的角色。退群在一个事务里删除该成员在本群的两类条目角色及群成员关系，保留内容和完成历史。即使是原创建者，请求也要重新满足当前成员资格。群主退群还须指定一位有效群成员接任。代价是入群的写入量随现有条目数增加；大群场景可考虑默认 viewer 加少量显式授权。

### 两个窗口都在编辑第 5 版，为什么不会静默覆盖？

带版本的 PATCH 到达后，事务内确认条目存在、用户仍在群内且有编辑权，再做条件更新。以下是 Todo 核心 SQL 的等价简写。

```sql
UPDATE todos
SET title = ?, version = version + 1
WHERE id = ? AND version = ?;
```

先写入的把版本改为 6。第二个仍带 5，影响行数为 0，在已确认资源存在的这条路径返回 409。客户端应重新读第 6 版，让用户确认修改。盲目替换版本重试会重新引入覆盖。SQLite 单写者只负责排队，无法知道后来的用户是根据五分钟前的界面作的决定。Todo 改自定义日期时，替换子表记录和更新主表版本在同一事务里。

### 周期待办为什么按需展开？

“每周一 09:00 站会”可以持续多年，写入时存开始时间和规则即可。查询时按群成员资格和时间先查候选，应用层用 rrule-go 在请求窗口展开。一次性条目直接取，自定义日期用指定日期拼原定时间，工作日和周末按星期过滤。后端日历入口以 `Asia/Shanghai` 解析日期。查 11 月 12 日传 `from=2026-11-12&to=2026-11-13`，区间左闭右开。这样次日零点只落入下一天。

Todo 是一个发生点；Event 有持续时间。11 日 23:00 到 12 日 01:00 的 Event 必须出现在 12 日视图里。相交条件是 `start < to && end > from`。对周期 Event，生成候选起点时要向前多看一个 duration，再做相交判断。恰好在 12 日零点结束的事件不命中。Calendar 顺序调两个 Service 合并结果，Todo 内部的规则和完成数据来自同一快照，整个聚合接口没有跨两个 Service 的统一事务。指定群的过滤目前在 handler 聚合后做，群多或窗口很长时会多做展开。

### 为什么同一天我已完成，同事仍显示未完成？

一行 `todo_completions` 唯一对应 `(todo_id, occurs_on)`；里面的 JSON 数组保存每个完成人的 user_id 和 completed_at。打卡在事务里检查当前群成员，从已验证身份确定操作人，首次标记还要确认这一天确实发生该任务。重复设为 true 不改第一次的完成时间；取消只移除自己的记录。读日历时批量取范围内完成记录，为当前用户建立“任务＋日期”的集合，再往展开实例上标记完成。多人挤在同一行会增加重写成本；如果用户规模变大，可以拆成一人一行，唯一键为 `(todo_id, occurs_on, user_id)`。

## 5. 登录、续期和退出怎样串起来

1. **注册。** 邮箱标准化，密码用 bcrypt，展示名允许重名，以“用户名＋五位后缀”区分。先查邮箱可提前提示，数据库的邮箱唯一索引和账号复合唯一索引才裁决并发冲突。候选后缀碰撞时可换一个再试，邮箱被占用直接返回冲突。
2. **登录。** 邮箱或完整账号均可登录。验证密码后签发 60 分钟的 HS256 access JWT，含用户 ID、签发者、签发时间和到期时间。refresh token 是 32 字节安全随机数，Redis 用其 SHA-256 摘要构造 key，值存用户 ID，TTL 七天。登录替换当前 Cookie 对应的旧会话，其他设备有独立会话。
3. **访问。** 中间件验证 JWT 的签名、允许的算法、签发者及到期要求，从中取用户 ID。普通业务接口验证身份时无需查询 Redis，读写资源要继续检查群成员和条目角色。
4. **续期。** refresh 从 HttpOnly、SameSite=Strict 的 Cookie 读取，Secure 由配置控制。Handler 查旧令牌、查当前用户、生成新 JWT，最终用 Lua 再检查旧 key 对应的人是否正确，先 `SET 新key EX ... NX`，成功再 `DEL 旧key`。两个请求即便先前的 Lookup 都成功，最终只有一个能消费旧 token。成功才向客户端发新 Cookie。刷新会重设七天 TTL。
5. **退出和失败语义。** 退出撤销当前 refresh 会话。已签发的 access JWT 可以存活到自身过期。两种错误要分开说：令牌无效是 401；刷新会话存储故障走 503。如果轮换已完成而响应丢失，旧 token 已经消费，客户端可能需要重新登录；代码关闭 Redis 客户端自动重试，避免重放有副作用的操作。

**常被连问。** JWT 签名保证能校验签发方和数据完整性，载荷可解码，所以别放密码。bcrypt 自带盐且有可调计算成本，适合低熵密码；refresh 本身是高熵随机值，SHA-256 用于摘要索引。HttpOnly 限制脚本读取 Cookie，Secure 限制 HTTPS 传输，SameSite 限制跨站附带。登录、刷新和退出还校验自定义请求头 `X-Note-Request: 1`，结合应用的同源部署；这个头本身不证明用户身份。

## 6. 搜索、头像和数据库选型

**群内搜索。** Todo 和 Event 的搜索共用计分查询。综合搜索先将两类匹配行 `UNION ALL`，标题完全相同 100 分、标题前缀 80、标题包含 60、正文包含 20，取首个命中的等级。按分数降序、更新时间降序、类型升序、ID 降序做全局分页。两张表分别取一页再拼，会把总体排名更高的条目排除在外。校验成员、统计总数、读取该页都在同一个只读事务中。SQL 参数绑定处理值与语句的边界，额外转义 `%`、`_`、`!` 让用户能搜索这些字面字符。两次翻页属于不同事务，期间数据更新仍可能让 offset 分页漂移。

**头像。** 后端限制输入大小为 5 MiB，先读图像配置验证 JPEG/PNG 和尺寸上限 4096×4096，再解码、居中裁剪、缩放为 512×512 JPEG。对象上传腾讯云 COS，SQLite 保存 URL。先上传新对象，再事务替换 URL；数据库失败尝试删新对象，提交后清理旧对象。删除失败记录日志，可能留下孤立文件。这是一个解释跨系统补偿的短例子。

**SQLite 的代价。** 本地文件适合这个部署形态，关系约束和事务覆盖了权限、日程、通知。启用 WAL 后，写入先追加到 WAL，checkpoint 再合回数据库文件；不同连接的读者与写者可并行，写者仍只有一个。项目将连接池上限设为 1，**本进程的读请求也会排队**。`busy_timeout(5000)` 给数据库锁竞争留出等待时间，连接池等待是另一层。`_txlock=immediate` 让写事务及早竞争写入资格。在事务回调中应一路使用 `tx`，调用外层 `db` 可能等待自己占用的唯一连接。[SQLite WAL](https://sqlite.org/wal.html) · [Go 数据库事务](https://go.dev/doc/database/execute-transactions)

## 7. 面试官的第二问：用项目回答八股

| 题目 | 可以直接说的答案 |
| --- | --- |
| 事务 ACID 在哪里体现？ | 原子性看入群、通知、Outbox 一起提交或回滚；一致性看外键、唯一约束和事务内业务规则；隔离性看搜索的 count 和列表读同一个快照；持久性看提交后的 Outbox 能在进程重启后继续扫描。SQLite 用了 WAL 和 NORMAL 同步，进程重启与极端掉电的保证要区分。 |
| 乐观锁、悲观锁、唯一索引各解决什么？ | 版本条件识别过期编辑；悲观做法会在竞争操作开始时拿锁，直到事务结束；唯一索引阻止两条重复记录。拿数据库写锁等待用户编辑会把交互时间带入事务，所以项目把版本发给调用方。 |
| 怎么选联合索引？ | 从查询的等值条件、范围和排序出发。示例是 `(group_id,user_id)` 查成员资格，`(todo_id,occurs_on)` 查单次完成记录。先看 `EXPLAIN QUERY PLAN` 是否使用预期索引；多建索引会增加写入和存储成本。 |
| N+1 是什么？ | 如果列出 50 条通知再逐条查询触发者，就会多出最多 50 次查询。快照查询用 GORM Preload 批量取关联；日历也先批量取完成数据再内存关联。预加载通常仍有多条 SQL，要保证同一快照需放进同一事务。 |
| Lua、Pipeline 有什么区别？ | Pipeline 主要减少往返；轮换 token 需要读取结果、判断并有条件地写新删旧。Lua 可以在 Redis 服务端完成这个判断，期间其他请求不会插入。脚本运行时错误没有关系数据库式自动回滚，通知脚本设置未完成标记，给恢复流程留下依据。大脚本还会延长其他请求等待时间。[Redis Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/) |
| Pub/Sub、Stream、Outbox 分别做什么？ | Pub/Sub 尽快通知在线订阅者，断线期间可能丢；Stream 保存有界的有序事件，可以按位置读；SQLite Outbox 保存事务已经承诺要投递的工作。这三者回答的是不同阶段的可靠性问题。[Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/) |
| 缓存击穿怎么处理？ | 同一用户收件箱失效，多个请求一起加载完整快照会放大数据库压力。按用户的短租约限制重建者数量；拿不到资格的读取者只再读一次。整个 Redis 进程不可用时，取得租约本身也会失败。 |
| 为什么重建锁必须有 token？ | A 的租约过期后 B 可能已经拿到锁，A 最后释放时必须比较 token，否则会删掉 B 的锁。租约只协调重建者；增量写入仍可进行，因此安装还要比较取得租约时的旧 state。 |
| 为什么 Hash 搭配 ZSet？ | Hash 可以直接按 ID 读卡片，ZSet 负责稳定的范围和倒序。按 ID 做分数时要考虑双精度浮点的整数精度，当前通知分页游标限制到 `2^53−1`。业务 revision 则以字符串传输和比较，避免大整数在 JSON/Lua 中失真。 |
| SSE 和 WebSocket 怎么选？ | 这里只需服务器主动通知，用户修改走常规 HTTP。SSE 在普通 HTTP 响应中传递事件，有 event、id、data 和心跳；WebSocket 更适合持续双向交互。选两者都还要自己设计鉴权过期、慢连接、丢消息后的恢复。 |
| 为什么 Hub 同时用 Mutex 和 channel？ | Mutex 保护“用户 → 连接”的共享 map，以及发送、移除、关闭之间的关系；channel 把事件交给对应连接。每连接容量 32，锁内用带 default 的 select 尝试发送，队列满则移除并关闭该连接，防止一个慢用户拖住整个 Hub。 |
| 关闭 channel 后会怎样？ | 剩余缓冲值可继续读，读尽后接收返回零值和 `ok=false`；向已关闭 channel 发送或重复关闭会 panic。Hub 在同一把锁下维护注册状态，取消订阅先检查连接还在不在，SSE 循环检查 `ok` 后退出。 |
| goroutine 如何退出？context 能杀掉它吗？ | 取消属于协作信号。worker、订阅者、SSE 都要观察 `ctx.Done()` 或使用支持 context 的调用。超时后的 Shutdown 另建 context；如果继承已经取消的停止信号，就没有时间让请求正常结束。 |
| Go 接口有什么实际用途？ | Calendar 在使用方只声明 Todo、Event 两个来源各自需要的方法，实际 Service 隐式实现。单测可注入假来源，单独验证聚合和错误传播。Handler 通过 Service 接口工作，避免把 GORM 查询和 HTTP 格式绑在一起。 |
| PATCH 怎么区分没传字段和零值？ | Todo 的可选更新字段用指针表达是否提供，Repository 按实际字段构造更新 map。比如不传 content 保留旧值，传空字符串按业务规则回退到最终标题。普通 JSON 指针字段对缺失和显式 null 都可能得到 nil，要区分两者需额外表示。 |
| 为什么报错要用 `%w` 和 `errors.Is`？ | Repository 在错误外面附加操作上下文，handler 仍能沿错误链匹配业务错误。举例：身份无效 401，有身份但没有权限 403，版本冲突 409，缓存恢复后仍不可用 503。 |
| 搜索数据量大怎么办？ | 前置群条件先缩小范围，`%关键词%` 通常难以利用普通 B 树标题索引缩小匹配范围。先检查执行计划和热点群大小，再评估 SQLite FTS5 及适合目标语言的分词。深分页还要考虑排序键和游标设计。 |
| 怎么扩容，先量什么？ | 先量连接池等待、日历候选数与展开耗时、最老未投递任务年龄、缓存重建耗时及 SSE 慢连接数。若写入排队主导，可迁移服务型关系库；若 worker 积压，可按接收者分区、有序消费并做任务领取。原 worker 串行遇错结束本轮，持续失败的头部任务会挡住后续用户。 |
